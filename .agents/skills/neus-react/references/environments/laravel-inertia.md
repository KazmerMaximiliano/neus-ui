# Laravel + Inertia + React

None of the owner's projects uses Laravel. This reference applies the house
conventions to the official Laravel React starter kit (Laravel 13, Inertia 3,
React 19, TypeScript; verified November 2026). It covers the React side only;
PHP code follows the project's own Laravel conventions.

## 1. Layout

```text
resources/
├── css/app.css                    global stylesheet: tokens, reset
└── js/
    ├── app.tsx                    createInertiaApp: layouts per page name
    ├── pages/                     Inertia entries only: kebab-case, default export
    │   └── settings/profile.tsx
    ├── views/<Name>Page/          profile B: page components (full contract)
    ├── features/<feature>/        profile C: presentation/{components,pages,hooks}
    ├── components/<Name>/         shared components (full contract)
    ├── components/ui/             shadcn/ui output (vendor; leave as generated)
    ├── layouts/<Name>Layout/
    ├── hooks/
    ├── i18n/                      i18n.md §6
    ├── lib/
    ├── types/global.d.ts          InertiaConfig augmentation
    └── routes/, actions/, wayfinder/   generated by Wayfinder (never edit)
```

- Generated or vendor code (`components/ui/`, Wayfinder output) keeps its
  generator's conventions, such as kebab-case files. Your own code follows the
  house contract next to it.
- Use the kit's `@/*` alias (`resources/js/*`).

## 2. Decide the styling system first

The kit ships Tailwind 4 and shadcn/ui, which conflict with the BEM +
`.styles.css` convention.

- **Existing project that kept Tailwind:** that is the project's styling system
  (precedence rule 2). Follow it and do not add BEM files beside it.
- **New project from the kit:** ask the user once whether to keep Tailwind +
  shadcn/ui or replace them with the house styling (`styling.md`). Never mix the
  two.

## 3. Pages and layouts

- Inertia resolves page names (`Inertia::render('settings/profile')`) to
  `resources/js/pages/settings/profile.tsx` through the `@inertiajs/vite`
  plugin. Those files are lowercase kebab-case and default-exported. Keep them as
  thin entries over a named `XPage`:

  ```tsx
  // resources/js/pages/settings/profile.tsx
  export { ProfileSettingsPage as default } from "@/views/ProfileSettingsPage";
  ```

- `XPage` lives in `views/` (profile B) or in the feature's
  `presentation/pages/` (profile C), and follows the page contract.
- Assign persistent layouts centrally in `createInertiaApp({ layout: (name) =>
… })` in `app.tsx`, by page-name prefix. Do not add per-page `.layout`
  functions; in Inertia 3 an arrow function assigned to `.layout` no longer
  works (use an array such as `[AppLayout]` if one page needs an exception).
- Layouts are components with the `Layout` suffix that follow the template
  rules: slots only, no data loading.

## 4. Props and shared data

- Type each page's props in `XPage.types.ts` with `readonly` fields mirroring
  what the controller sends. The controller is the boundary that validates
  data, so the page trusts its props.
- Type shared props once by augmenting Inertia's config (an allowed
  declaration-merging `interface`):

  ```ts
  // resources/js/types/global.d.ts
  declare module "@inertiajs/core" {
    export interface InertiaConfig {
      sharedPageProps: {
        readonly name: string;
        readonly auth: Auth;
        readonly locale: Locale;
        readonly translations: Translations;
      };
    }
  }
  ```

- Read shared props with `usePage()` inside hooks (`useAuth`,
  `useTranslations`), not directly in many components.

## 5. Routes and forms

- Never hardcode URLs. Use the Wayfinder functions the kit generates
  (`import { store } from "@/routes/login"`, `href={register()}`). Use Ziggy's
  `route()` only if the project already uses Ziggy.
- Use Inertia's `<Form>` component with Wayfinder (`<Form {...store.form()}>`
  with a render prop giving `{ processing, errors }`), or `useForm(store(), …)`
  when you need imperative control. Do not hand-roll fetch calls for page forms.
- Validation errors come from Laravel already localized (`lang/<locale>/
validation.php`). Display them beside their field with `aria-invalid` and
  `aria-describedby`.

## 6. Environment, SSR and tooling

- Only `VITE_*` variables reach the client.
- SSR: the Vite plugin reuses `app.tsx` as the SSR entry. Add a separate
  `ssr.tsx` only for a manual setup. Because of SSR, browser APIs belong inside
  effects and handlers.
- The kit may run Vite through its own toolchain wrapper and `composer` scripts
  (`composer dev`). Use the scripts that exist in `package.json` and
  `composer.json`.

## 7. Tests and validation

- The kit ships PHP tests (Pest), not JS tests. Add Vitest + Testing Library
  only when the user agrees. Until then, report that the React side has no test
  runner.
- Validate with the scripts that exist: typically lint, `types` or typecheck,
  `build` (and `build:ssr`), plus `php artisan test` for the backend.
