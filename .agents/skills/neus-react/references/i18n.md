## 1. Rules for every host

**First, decide whether i18n applies.** If the project already has an i18n
setup, or ships more than one locale, use it (sections 3–6 cover each host). If
it is a single-locale project without i18n, do not build one: keep the copy in
the parent that renders the component (an `.astro` file, a page or route entry)
or in a `.consts.ts`, and pass it to React components as props. Scaffold i18n
only when the user asks for a second locale.

When i18n applies, these rules hold in every host:

- **No hardcoded user-facing text** in application components: visible copy,
  `aria-label`, `title`, `alt`, placeholders and toast or error messages all go
  through i18n.
- **English (`en`) is the default and fallback locale for a new setup with no
  other signal; Spanish (`es`) is the second.** The user's request, the
  project's existing default (its i18n config) or the language its current
  content is written in (`<html lang>`, existing copy) wins, and a project that
  declares other locales keeps them. Adding a locale never changes the existing
  default: the default decides which URLs carry a locale prefix, so changing it
  moves every current page.
- **One file per feature (or per core presentation concern) per locale.** No
  monolithic locale files. Filenames and keys match exactly across locale
  directories.
- **A project that already keeps one file per locale** (`messages/en.json`,
  `locales/en.json`) keeps that structure: add the feature's namespace to each
  locale file, with the same keys in all of them. Do not migrate as a side
  effect, because the split touches the loader and every existing feature. In
  the delivery, suggest the per-feature split and the parity test as a separate
  change.
- **Keys are namespaced by feature:** `<feature>.<key>` (`projects.deploy`,
  `settings.profile.title`).
- **Add copy to every locale in the same change.** Never leave a key in one
  locale only.
- **Type the keys from the complete resource map.** No single language is the
  source of truth for the type: enforce parity symmetrically with a test that
  compares key sets across all locales.
- **Use the library's API directly.** Do not wrap or redefine its hooks,
  providers or `t` functions, and do not build a custom translation engine where
  the host has one.
- **i18n belongs to presentation.** Domain entities, use cases, services and data
  adapters never import translations or the i18n runtime. Locale-dependent
  display utilities (date, number and relative-time formatting with `Intl`)
  live in presentation too.
- **Set `<html lang>`** to the language of the rendered content.

## 2. Localized structured content

Long-form or structured content that is not UI copy (experience entries, project
lists, legal documents, blog posts) does not belong in translation files. Use one
of these instead:

- The host's content system: Astro content collections, MDX, or a CMS.
- A typed content module inside the component that renders it:

  ```text
  Projects/
  ├── index.ts
  ├── Projects.tsx                   imports from "./projectsContent"
  └── projectsContent/               folder module (code-style.md §4)
      ├── index.ts                   export { getProjectsByLocale }; export type { ProjectItem }
      ├── projectsContent.ts         getProjectsByLocale(locale)
      ├── projectsContent.types.ts   the item type
      ├── projectsContent.en.ts      export const PROJECTS_EN: readonly ProjectItem[]
      └── projectsContent.es.ts      export const PROJECTS_ES: readonly ProjectItem[]
  ```

Every locale exports the same shape. The selector falls back to `en`. Do not
name these files `.data.`: in the hexagonal profile, that infix marks the data
layer (`<feature>.data.types.ts`).

## 3. Vite SPA: i18next + react-i18next

```text
src/core/presentation/i18n/        (profile B: src/i18n/)
├── index.ts              export { i18n } and the public locale types
├── i18n.ts               initialization and runtime configuration
├── i18n.types.ts         locale and resource contracts; CustomTypeOptions
└── locales/
    ├── index.ts          export { RESOURCES, … }
    ├── locales.ts        assembles every JSON resource
    ├── en/<feature>.json
    └── es/<feature>.json
```

`i18n/` and `locales/` are folder modules (`code-style.md` §4): other code
imports `./i18n` or `#core/presentation/i18n`, and `i18n.types.ts` imports
`./locales`. The barrel must re-export at least one runtime value from `i18n.ts`
(the instance). A barrel with only `export type` lines compiles to an empty
file, and then `import "./i18n"` would never run the initialization.

- Use `i18next` with `react-i18next`.
- Components import `useTranslation` from `react-i18next`. Non-React code uses
  the `i18next` instance or receives its native `TFunction`. Language changes go
  through `i18n.changeLanguage`.
- The initialized singleton is enough. Do not add an app-specific provider, and
  do not wrap `useTranslation`, `I18nextProvider`, `t` or `changeLanguage`.
- Assemble JSON resources only in `locales/locales.ts`. Configure
  initialization, persistence, fallback (`fallbackLng: "en"`), interpolation and
  React integration only in `i18n.ts`.
- Type keys by augmenting i18next's `CustomTypeOptions` with the complete
  resource map (a declaration-merging `interface`, the allowed exception). Do not
  create parallel translation-function types.
- Import the i18n module once at the app entry (`import "./i18n";` in
  `main.tsx`) before rendering.

Use a single `translation` namespace whose top-level groups are the features, so
keys read `projects.deploy`:

```ts
// locales/locales.ts
import enProjects from "./en/projects.json";
import esProjects from "./es/projects.json";

export const EN_TRANSLATIONS = { projects: enProjects } as const;
export const ES_TRANSLATIONS = { projects: esProjects } as const;

export const RESOURCES = {
  en: { translation: EN_TRANSLATIONS },
  es: { translation: ES_TRANSLATIONS },
} as const;
```

```ts
// i18n.types.ts
import type { EN_TRANSLATIONS, ES_TRANSLATIONS, RESOURCES } from "./locales";

type LocaleResources = typeof RESOURCES;
type ResourceKeys<Resource> = {
  readonly [Group in keyof Resource &
    string]: `${Group}.${keyof Resource[Group] & string}`;
}[keyof Resource & string];
type EnKeys = ResourceKeys<typeof EN_TRANSLATIONS>;
type EsKeys = ResourceKeys<typeof ES_TRANSLATIONS>;
type AssertTrue<Value extends true> = Value;
// Fails to compile when either locale has a key the other lacks.
type MatchingLocaleKeys = AssertTrue<
  [Exclude<EnKeys, EsKeys> | Exclude<EsKeys, EnKeys>] extends [never]
    ? true
    : false
>;

export type Locale = keyof LocaleResources;
export type TranslationResources = MatchingLocaleKeys extends true
  ? LocaleResources[Locale]["translation"]
  : never;

declare module "i18next" {
  interface CustomTypeOptions {
    readonly defaultNS: "translation";
    readonly resources: { readonly translation: TranslationResources };
  }
}
```

The compile-time assertion checks the first level of keys. Nested keys and
interpolation placeholders still need the runtime parity test from §1.

## 4. Next.js: next-intl

next-intl v4 with locale-prefixed routing (`app/[locale]/…`), verified November 2026.

```text
messages/
├── en/<feature>.json          plain keys for one feature
└── es/<feature>.json
src/
├── i18n/
│   ├── routing.ts             defineRouting({ locales: ["en", "es"], defaultLocale: "en" })
│   ├── navigation.ts          createNavigation(routing): Link, redirect, useRouter…
│   ├── messages/              assembles per-feature files into one map per locale
│   │   ├── index.ts
│   │   ├── messages.ts
│   │   └── messages.test.ts   key parity across locales
│   └── request.ts             getRequestConfig: resolves the locale, returns messages
├── proxy.ts                   export default createMiddleware(routing) + matcher
└── global.ts                  AppConfig augmentation
```

Here `i18n/` is a responsibility folder holding separate modules, not one
module, so it has no `index.ts` of its own. Each module inside follows the
module rule: `routing.ts` and `navigation.ts` stay flat, and `messages`
becomes a folder because it has a test. `request.ts` always stays a flat file
at that path, because the next-intl plugin loads it from there. Importers
write `@/i18n/routing`, `@/i18n/navigation` and `./messages`.

```ts
// src/i18n/messages/messages.ts
import enSettings from "../../../messages/en/settings.json";
import esSettings from "../../../messages/es/settings.json";

export const EN_MESSAGES = { settings: enSettings } as const;
export const ES_MESSAGES = { settings: esSettings } as const;

export const MESSAGES = { en: EN_MESSAGES, es: ES_MESSAGES } as const;
```

```ts
// src/i18n/request.ts
import { hasLocale } from "next-intl";
import { getRequestConfig } from "next-intl/server";
import { notFound } from "next/navigation";
import * as rootParams from "next/root-params";
import { MESSAGES } from "./messages";
import { routing } from "./routing";

// next-intl loads this module through its default export.
export default getRequestConfig(async ({ locale }) => {
  const candidate = locale ?? (await rootParams.locale());
  if (!hasLocale(routing.locales, candidate)) notFound();

  return { locale: candidate, messages: MESSAGES[candidate] };
});
```

- `next/root-params` is enabled by default from Next 16.3. On older versions,
  use the project's existing `requestLocale` pattern.
- Server Components use `getTranslations` (`next-intl/server`). Synchronous
  components, server or client, use `useTranslations("settings")`. Use the
  library's hooks directly.
- Render `<NextIntlClientProvider>` without props in `app/[locale]/layout.tsx`.
  Since v4 it passes locale and messages down automatically. Use
  `messages={pick(…)}` when the client should receive fewer messages.
- Navigation uses the `Link`, `redirect` and `useRouter` from
  `i18n/navigation.ts`, never the raw `next/link` for localized routes.
- Type messages in `src/global.ts` by augmenting `AppConfig` (allowed
  declaration merging). Set `Locale` to `(typeof routing.locales)[number]` and
  `Messages` to the parity-checked type built from `MESSAGES` with the symmetric
  assertion from §3.

## 5. Astro: i18n routing + typed dictionary

URL routing uses Astro's built-in i18n. UI copy uses a typed dictionary, adapted
from Astro's official i18n recipe and split per feature.

```js
// astro.config.mjs
export default defineConfig({
  i18n: {
    locales: ["en", "es"],
    defaultLocale: "en",
    routing: { prefixDefaultLocale: false },
  },
});
```

```text
src/i18n/
├── index.ts            export { useTranslations, … }; export type { Locale, … }
├── i18n.ts             useTranslations(locale) and locale helpers
├── i18n.types.ts       Locale, Translations
└── locales/
    ├── index.ts
    ├── locales.ts      assembles the per-feature dictionaries
    ├── en/<feature>.ts export const HERO_EN = { title: "…" };
    └── es/<feature>.ts export const HERO_ES = { title: "…" };
```

As in Vite, `i18n/` and `locales/` are folder modules: frontmatter imports
`../../i18n`, never `i18n/i18n`. The per-locale dictionaries are single files
and stay flat.

- Read the active locale from `Astro.currentLocale` and build links with
  `getRelativeLocaleUrl(locale, path)` from `astro:i18n`. Never concatenate
  locale prefixes by hand.
- `useTranslations(locale)` returns a `t(key)` that falls back to `en`. Call it
  in frontmatter.
- Type `Translations` from the assembled map in `locales.ts` and reuse the
  symmetric key assertion from §3, so that neither locale becomes the source of
  truth. Still add the runtime parity test.
- **Islands** receive already-translated strings (`labels={{ … }}`) or the
  `locale` as a serializable prop. They do not boot react-i18next.
- Localized long-form content goes in content collections, one folder per
  locale (`src/content/legal/en/…`).
- A single-locale site without this setup keeps its copy in the `.astro` files
  (see the decision at the top of §1).

## 6. Laravel + Inertia: Laravel translations

Laravel owns translations. React receives them as shared Inertia props. This is
adapted to the house rules; the starter kit ships no i18n.

```text
lang/
├── en/<feature>.php           return ['deploy' => 'Deploy', …];
└── es/<feature>.php
app/Http/Middleware/HandleInertiaRequests.php   shares locale + translations
resources/js/i18n/useTranslations/   hook module, imported as @/i18n/useTranslations
├── index.ts
├── useTranslations.ts         reads shared props, returns t(key, replacements)
└── useTranslations.types.ts
```

- One PHP group file per feature per locale. Laravel's `group.key` addressing is
  the house `<feature>.<key>` scheme, and the backend's `__('projects.deploy')`
  uses the same keys.
- Set `APP_LOCALE=en` and `APP_FALLBACK_LOCALE=en`. Resolve the user's locale in
  middleware (`App::setLocale`).
- `HandleInertiaRequests::share()` shares `locale` and the translation groups
  the frontend needs. Share only frontend groups, not `validation.php` or
  `auth.php`.
- `useTranslations` is the single thin bridge from shared props to `t()`:
  dotted-key lookup, `:placeholder` replacement and a fallback to the key. Keep
  it that small, and add a dependency only if the user asks for one.
- Type `translations` in the `InertiaConfig` `sharedPageProps` augmentation
  (`laravel-inertia.md` §4). Enforce parity with a backend test that compares
  the group keys across `lang/en` and `lang/es`.

## 7. Libraries

A component library ships no translation runtime:

- Every user-facing string (labels, aria-labels, empty states, error messages)
  is configurable through props, or through a locale object passed to a provider.
- Defaults must not lock consumers into the developer's language. Prefer
  generating text from `Intl` (`Intl.DateTimeFormat`, `Intl.NumberFormat`,
  `Intl.DisplayNames`) with a `locale` prop, and keep any literal defaults in
  `.consts.ts` where they are easy to override.
